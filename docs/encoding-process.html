Runbook

How we encode VR video for Serene

FOR — Serene dev team PLATFORM — macOS TARGET — Meta Quest 3S

Serene's VR videos were reported as fuzzy in the headset. The cause was two unrelated faults in the source files, both now understood. This is the process that fixes them — measured against the actual device rather than vendor guidance, and packaged as scripts you can run on any Mac.

Setup

Two commands

brew install ffmpeg
./check_setup.sh

Only ffmpeg and python3 are required — the Python tools need no third-party packages. adb is optional, for headset testing. check_setup.sh reports anything missing with the exact command to fix it.

It specifically checks that your ffmpeg includes libsvtav1. Some builds ship without it, every encode depends on it, and without this check the failure surfaces halfway through a long batch.

The workflow

Inspect, encode, verify

  1. Inspect first — always

    ./inspect_master.sh /path/to/masters/

    Read-only and takes seconds. Tells you what each file actually is and what it will become. Vendors ship a mix of 360°/180°, mono/stereo and 30/60 fps, and files are sometimes mislabelled — worth knowing before starting encodes that run for tens of minutes each. Anything ambiguous is flagged rather than guessed at.

  2. Encode the batch

    ./encode_vendor.sh /path/to/masters/
PRESET=8 ./encode_vendor.sh ...   # ~2x faster, small quality cost

    Detects each file's format and picks the right target automatically. Roughly 0.3× realtime on Apple Silicon — about 50 minutes per 15-minute title — and several times slower on Intel.

  3. Verify before uploading

    ./verify_final.sh final/output.mp4 master.mp4

    Checks the 360 metadata survived, the index sits before the media, the file decodes cleanly end to end, and measures quality at six points across the full running time — so a demanding stretch that starved the encoder cannot slip through unnoticed.

The standard

AV1 · ~16 pixels per degree · ≤35 Mbps

Source formatOutputBitrate
360° stereo top-bottom, 30 fps5760×576034 Mbps
360° stereo top-bottom, 60 fps5152×515235 Mbps (capped)
360° mono, 30 fps5760×288017 Mbps
VR180 stereo side-by-side, 30 fps5760×288017 Mbps

Sources already below target are never upscaled. Every output gets a faststart index and has its 360/stereo metadata restored.

Prefer 30 fps masters for 360° content. At 60 fps, holding quality constant would need ~55 Mbps — past the budget — so it gets capped and comes out softer. VR180 does not have this problem: it covers a quarter of the sphere, so 60 fps fits the budget at full quality. If a vendor offers the same scene in VR180, it is the better buy.

Worth knowing

Two things that are easy to get backwards

Resolution is the wrong unit — use pixels per degree

A flat 4K video puts 3840 pixels across the screen. A 360° video spreads those same pixels around the viewer's entire head, and the headset shows only ~96° at a time.

So a 4K 360° video delivers 10.7 px/deg against the Quest 3S's ~19.1 — about half the detail the display can resolve. This is why an ABR ladder designed for flat video under-serves VR, and it is the single most useful idea to carry into any decision about VR video quality.

At a fixed bitrate, more pixels make quality worse

In our seven-way A/B on the headset, an 8K encode at 45 Mbps scored lowest of all. Spread across 59 megapixels, every pixel is starved. A 4608² encode at the same bitrate as a 5760² one was indistinguishable.

If something looks soft, the lever is bitrate or codec — not resolution. Raising resolution within a fixed budget actively hurts.

What went wrong originally

Two faults, same symptom

Both titles looked "fuzzy". The causes were unrelated, which is the argument for auditing the library with inspect_master.sh rather than fixing titles one complaint at a time.

London — over the decoder's bitrate limit

Encoded at 251 Mbps against the Quest 3S's 220 Mbps H.264 ceiling, with a nonstandard profile level. The decoder cannot keep up and playback falls back to a degraded path.

Fixed by re-encoding to AV1 at 30 Mbps — 29 GB → 3.3 GB, at better measured quality.

Animals Compilation — mono video labelled as stereo

The file is a normal mono 360° frame but was tagged top-bottom stereo. A player honouring that tag splits one image in half and sends the sky to one eye and the ground to the other, stretching each 2× vertically. Half the resolution, plus two eyes that cannot fuse.

Proof: PSNR between the two halves was 7.1 dB, where genuine stereo measures ~25 dB. The file was otherwise healthy — nothing wrong with its encoding at all.

Troubleshooting

The failure modes we actually hit

Video plays flat, or as two stacked images

The 360 metadata is missing. FFmpeg discards it on every output, including -c copy — that is FFmpeg's mov muxer, not a bug in the toolkit. inject_spatial.py restores it and the scripts always run it. Never upload a file that has not been through verify_final.sh.

A square file is flagged for review

A square frame with no stereo tag is genuinely ambiguous — 360° stereo top-bottom, or VR180 mono. The tool assumes top-bottom 360°, correct at 8K sizes, and flags it. This comes up often because any FFmpeg pass strips the tag.

To check: if the top and bottom halves show near-identical images, it is stereo; if they show different parts of the scene, it is mono.

AV1 output is below the requested bitrate

Expected, not a fault. SVT-AV1's VBR stops once it hits its quality target, so easy content lands under budget — the target was met with fewer bits.

Sideloaded files don't appear on the headset

They land in the Gallery app, not Files. Use ./play.sh <name> to launch one directly from the Mac.
